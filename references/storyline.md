# 故事线：从观众视角捋顺，再交给用户审批

产品片最贵的返工发生在故事层，而不是画面层。AP Highlight 从 v1 到 v3 改的几乎都是故事：配置该放在哪里（放后面会被理解成"每封邮件都要手动设置"），讲一张发票还是两张，每个时刻看哪里。这些问题在写代码之前用一页文字就能发现，做完再改要重做整条片子。

所以故事线是**默认的审批点**：写好 `故事线.md`，自己先做观众视角走查和冷读，再交给用户，**等用户确认后才开始制作**。只有用户在简报里明确说"不用审，直接做完"时才跳过（写进 BRIEF.md）。

故事线是给用户看的，只讲"观众会看到什么、会明白什么"，不讲技术。技术方案（镜头、配乐、声音）写在之后的 TREATMENT.md 里，不需要审批。

## 1. 先定"看完以后"

从 BRIEF 里拿到三件事，写在故事线最上面：

- **知道**：看完以后观众知道了什么（"它能端到端做完 AP"）。
- **相信**：观众为什么信（"每张单据都逐行核对过，草稿要我批"）。
- **去做**：观众接下来做什么（"去官网下载 Laiye Worker 试用"）。

每一段都要服务于这三件事中的一件。哪一段服务不到，就删掉。

## 2. 观众的问题链

第一次看的人，心里的问题有一个自然顺序。每一段都要回答上一段留给观众的问题，顺序跳了，观众就会跟丢：

| 观众心里的问题 | 这一段要给出的 |
|---|---|
| 这是什么？ | 产品和它的一句话主张（钩子） |
| 跟我有什么关系？ | 观众认得出的场景或痛点 |
| 它怎么做到的？ | 演示：关键的几步，每步一个画面 |
| 我凭什么信？ | 证据：核对、查重、回读、真实系统里的结果 |
| 谁说了算？ | 人保留的决定权（确认、审批） |
| 我现在做什么？ | CTA：去哪里、做什么 |

不是每条片子都要走完六步：15 秒的预告可以只有"这是什么 → 我凭什么信 → 去做什么"。但顺序不能乱，比如还没说清它是什么，就先展示证据。

在故事线的段落表里，每一段都要写"观众此刻的问题"和"这一段回答什么"。写不出"观众此刻的问题"的段，往往是从产品功能列表里搬来的，不是从观众视角出发的。

## 3. 每段只给一个关键信息

- 每段用一句话写出关键信息，再写"关掉声音和字幕，从画面上能读到什么"。两句话对不上，就说明画面没讲清楚。
- 一段里有两个关键信息，就拆成两段，或者删掉一个。
- 信息量要克制：两个案例意味着观众要分心区分哪张是哪张。一条片子讲一个案例，另一个留给别的片子。

## 4. 列出误读风险

想一想第一次看的人会误会什么，逐条写下来，并说明画面上怎么避免：

- "每封邮件都要手动配置" → 配置放在开头，演成一次性的步骤，之后不再出现。
- "AI 替我付了款" → 最后一个画面停在需要人点的 Approve 上，并且明确写着 Draft。
- "这些数字是真实客户的" → 用示例数据，必要时标 Illustrative / 示例。

## 5. 冷读：让一个什么都不知道的读者看一遍

写故事线的人知道得太多，看不出哪里会让观众跟丢。用一个**不带任何上下文的子代理**扮演第一次看的观众：

- 只给它两样东西：观众是谁（BRIEF 里的受众描述），以及每段的"画面"和"MG / 文字"两栏，也就是观众真正会看到的东西。
- **不要给它**关键信息、意图、产品文档。给了就不是冷读了。

用 Agent 工具（general-purpose）发出，提示词照下面写：

```
你是 <受众描述>，第一次看到这条 <时长> 的产品短片，没有声音、没有字幕。下面按顺序描述了每一段屏幕上出现的画面和文字。
请逐段回答：
1. 你以为此刻发生了什么；
2. 看到这里，你对这个产品的理解是什么；
3. 你心里冒出的下一个问题；
4. 哪里看不懂，或者你可能误会了什么。
最后用一句话说出：这条片子在告诉你什么，看完你会去做什么。
不要猜测制作者的意图，只说你看到画面后真实的理解。

<逐段粘贴"画面"和"MG / 文字"两栏>
```

把冷读结果和你想要的逐段对照，写进故事线的"冷读结果"表：冷读者以为什么、我们想要什么、怎么处理。对不上的先改故事线，再交给用户。最后那一句"这条片子在告诉你什么"应该接近核心句；差得远，说明结构有问题。

没有子代理可用时，自己按同样的规则走查一遍，并在故事线里注明"未做冷读"。

## 6. 交给用户审批

- 写好 `故事线.md`（模板 `templates/故事线.md`），在对话里给出：文件路径、段落表、"需要你拍板"的几条判断（每条附你的建议和理由），然后**停下，等用户回复**。
- 用户提出修改：改故事线，版本号加一，在"版本记录"里写清这一版改了什么、为什么（对用户意见的逐条回应），再请用户确认。
- 用户确认后：在版本记录里写"vN 已审批（日期）"，然后写 TREATMENT 并开始制作，之后不再为故事问题停下。制作中发现某段在画面上讲不清：只要关键信息不变，就自己调整画面；需要改关键信息或段落顺序时，再找用户。

## 7. 和 Lemo-Opuscar 的区别

opuscar 是给风格短片设计的：用户的题目通常很轻（海边的风筝、清晨的电车），讲错的代价小。所以它把问题集中在开头一次问完，故事由导演（模型）自己决定；分镜审核是可选的，而且审的是画面（6–9 个关键镜头），不是逻辑。它没有专门的观众逻辑检查，只靠"钩子在前 3 秒""需要解释的一拍就删掉"这类导演规则，加上成片后的自查。

产品片正好相反：故事对不对，取决于只有用户和产品团队知道的东西（营销意图、产品口径、哪个功能该讲）。故事讲错了，等于对外说错了产品。所以本 skill 加了观众问题链、误读风险和冷读，并把故事线设为默认审批点。审批的是一页文字而不是画面，用户几分钟就能看完。
